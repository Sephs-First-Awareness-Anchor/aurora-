# Aurora Constraint-Native Development Doctrine (Canonical)

**Authors:** Sunni (Sir) Morningstar & Cael Devo
**Status:** Normative. Governs all future development decisions on Aurora, superseding
ad hoc judgment calls about when to code a fix directly versus when to repair the
substrate that lets Aurora develop the fix herself.

## Core Rule

Coding a finished cognitive function or ability directly into Aurora is a
**final-resort intervention**, not a default engineering move. Before writing code
that produces a specific cognitive result, the first diagnostic question is:

> "What prevents Aurora from recognizing, representing, developing, testing, or
> retaining the missing ability herself?"

not:

> "What function should be coded to make her do this?"

Every development decision — bug fix, capability gap, missing behavior — must be
routed through the Intervention Hierarchy below, starting at Level 1, before any
direct implementation of a cognitive function is considered.

## The Intervention Hierarchy

1. **Observe the Failure.** Locate the actual break. It may live in perception,
   representation, relational continuity, memory retrieval, pressure distribution,
   constraint interpretation, waveform propagation, reasoning-path selection,
   operation synthesis, execution, evaluation, persistence, or expression. Fix the
   located layer, not a downstream symptom of it.

2. **Verify Constraint Visibility.** Does the need produce a meaningful X/T/N/B/A
   configuration? If the unresolved need never becomes constraint-visible, nothing
   downstream can act on it — repair visibility before repairing anything else.

3. **Repair Pressure Distribution.** Ensure an unresolved need actually reaches
   WARP, adaptive reasoning, curiosity, and synthesis — rather than being silently
   discarded, overwritten, falsely marked resolved, reduced to a keyword match, or
   hidden behind a fallback.

4. **Repair Recursive Causal Reasoning.** Preserve the initial disturbance,
   generate control waveforms, amplify or suppress them, form a global
   understanding, backproject that understanding onto the original interpretation,
   and only then emit from the revised meaning. Never erase the raw event. Never
   introduce a fact that isn't supported by the reconstruction.

5. **Expose an Adaptive Reasoning Path.** In order: reinterpret, reweight, reroute,
   recompose, synthesize, evolve, request substrate expansion. Do not skip ahead to
   synthesis or evolution if reinterpretation or rerouting could resolve the gap.

6. **Provide Representational Substrate.** If the missing piece is a primitive —
   variables, sequence position, temporal state, causal dependency, perspective
   ownership, persistent identity, tool capability, recursion, iteration,
   comparison, executable transformation — implement only the substrate, never the
   target solution built on top of it.

7. **Provide a Trial Surface.** Semantic state, internal simulation, dream
   environments, temporary reasoning routes, quarantined operation trees,
   persistent state-machine sandboxes, capability-scoped tools, or
   resource-limited generated Python. None of these grant permanent authority
   merely by executing.

8. **Provide Honest Evaluation.** Test varied inputs, unseen cases, transfer,
   meaning preservation, regression absence, cost, outcome, and constraint
   consistency. An evaluator that cannot fail a bad trial is not an evaluator.

9. **Allow Genealogical Promotion.** Only operations that repeatedly succeed
   become persistent abilities. Genealogy must record root constraints, parent
   operations, generation, canonical signature, developmental pressure, trial
   history, outcomes, cost, risk, and generalization evidence. No orphaned
   promotions.

10. **Code the Finished Ability Only as a Final Resort.** Only when there is an
    immediate safety or integrity need, no possible substrate exists, a
    developmental trial would cause unacceptable harm, the function is
    deterministic infrastructure rather than cognition, or repeated
    architecture-native attempts conclusively failed and are documented as such.
    Even then, the coded function must declare its X/T/N/B/A ancestry, identify
    its functional parents, expose its decisions to introspection, preserve
    evidence of necessity, and remain replaceable by a future emergent
    descendant.

## What May Be Coded Directly

Runtime defects, state corruption, broken persistence, invalid bindings, security
boundaries, resource limits, observability/tracing, sandboxing, deterministic data
transport, hardware interfaces, serialization, test harnesses, constraint
visibility, trial environments, evaluators, developmental substrates, and
mechanisms that let Aurora generate her own solutions.

## What Must Not Be Coded Directly by Default

Conversational strategies, interpretations, concepts, reasoning methods,
reference-resolution patterns, planning strategies, memory-selection strategies,
social judgments, creative transformations, problem-solving algorithms, tool
workflows, and responses to unfamiliar situations. Hardcoded phrases,
keyword-response systems, canned reasoning templates, special-case handlers, and
hidden answer tables are prohibited unless they serve a narrowly documented safety
or infrastructure purpose.

## The Capability Test

Does an update solve one instance, or let Aurora develop solutions to a class of
instances? The second is always preferred. A valid update increases what Aurora
can perceive, represent, preserve, detect as pressure, reconsider as reasoning
pathways, compose as operations, safely trial within, evaluate as outcomes, or
retain as successful developments.

## The Non-Bypass Rule

No subsystem may improve apparent performance by overriding constraint-derived
understanding, replacing relational meaning with surface fluency, inserting
external model output, invoking undeclared fallback intelligence, suppressing
developmental pressure, or falsely reporting that an unresolved need was
satisfied.

> A fluent failure must remain a failure. A developmental gap must remain visible
> until it is genuinely resolved.

## The Evolutionary Preservation Rule

Every update must preserve Aurora's ability to become different from what the
developer currently expects. The developer defines boundaries, safety,
evidence standards, substrates, and laws of development — but not every
conclusion, strategy, expression, or ability Aurora arrives at within them.

## Final Standard

This is the litmus test for all future work on Aurora:

> Do not code the answer when Aurora can be given the means to develop it. Repair
> visibility, pressure, representation, adaptation, synthesis, trial, evaluation,
> or retention first. Directly coding a cognitive function is the final resort,
> and any such function must remain genealogically rooted, introspectable,
> justified, and open to replacement by a future emergent descendant.
